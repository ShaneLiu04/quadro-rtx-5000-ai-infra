# AR003 gemm-sweep 实验结果日志

机器：Quadro RTX 5000（sm_75, 48 SM, 16GB, HBM 448 GB/s, L2 4MB）｜torch 2.5.1+cu121（Windows）
峰值口径：FP32 11.2 TFLOPS / FP16 TC 89.2 TFLOPS / INT8 TC 178.4 TOPS / clock 1815 MHz
计时纪律：2s 会话烧机（时钟爬坡）→ 每配置 3 次 warmup → 自适应 reps（~1s/配置，clamp [3,10]）→ 3 pass 取中位数；CUDA Event 打点。E6 用 per-iter event 协议（控制缓存态，绝对值含同步开销，仅组内可比）。
正确性门：INT8 精确对拍（不可用，见 E5）；FP16 对 double 参考 ≤1.5 ulp@max|ref|；E2 skinny 对 CPU double；E3 部分和重构；E4 bmm-vs-flat 等价；E7 无隐式拷贝断言 + 同数学断言。全部门先行通过才计时。
全部数据在 `results/*.json`，本文件引用数字与 JSON 一致。

## fig1a — 形状网格热图（E1a，K=2048，FP32）

**数据**：49 格全实测；对角线 0.54 → 2.32 → 5.70 → 8.58 → 10.01 → 9.06 → 9.68 TF（64→4096）；全域 min 0.54（64,64），max 10.24（1024,2048）。

**分析**：
1. **小形状完全由调度/launch 主导**：64×64 只有 0.54 TF（4.8% 峰值）——flop 太少（2·64³=0.5 MFLOP），0.031ms 里 kernel launch + tile 装载占绝对大头。这不是「cuBLAS 慢」，是**问题太小**。
2. **进入满波后迅速饱和到 9.5-10.2 TF**（85-91% 峰值）：M,N≥512 的内部区域基本平坦——cuBLAS 的 tile 选择在方ish 区域非常稳健。
3. **M/N 不对称**（同一 K 下）：M=64,N=4096 = 7.97 TF vs M=4096,N=64 = 5.92 TF。两者 flop 相同、tile 数相同（模型 32 个），但行主布局下 **N-skinny（输出 4096×64）每 tile 的写回列窄、B 矩阵（2048×64）跨行读取复用差**，比 M-skinny 更难喂饱。结论：**skinny 的方向也有讲究**（对 row-major 输出，M 小比 N 小更友好）。
4. **2048 对角微凹**（(2048,2048)=9.06 vs (1024,1024)=10.01、(1024,2048)=10.24 区域最高）：256 tile = 5.33 波，量化上界利用率 256/⌈5.33⌉÷48 = 256/288 = 88.9% → 损失 ~11%，与 9.06 vs 10.24（-11.5%）相当吻合。两个 256-tile 格恰好都是凹陷 trio 之二（(2048,2048)=9.06、(1024,4096)=8.90），wave 量化与启发式差异在此重叠，单凭此图无法分离；第三个凹陷 (512,512)=8.58 只有 16 tile/0.33 波，量化模型预测损失 67% 而实测只 -16%——**cuBLAS 对 sub-wave 形状内部 split-K 救回来了大半**（与 E3 结论互证）。
5. **wave 等值线（红色网格）与实测台阶对齐但不精确**：128×128 只是模型假设，cuBLAS 实际可用 128×256/256×128 等多种 tile，量化边界比模型更模糊——这本身就是「库启发式存在」的证据。

## fig1b — wave 量化阶梯（E1b，N=K=4096，细粒度 M）

**数据**：M=64→7.96，96→9.15，128→9.67（以上 tiles=32）；160→8.66，192→10.12，224→8.84，256→9.98（tiles=64）；320→10.15，384→10.45（tiles=96）；512→9.00（tiles=128）；768→9.84 一直到 2048→9.96（tiles≥192）。

**分析**：
1. **tiles=32 → 64 处出现真台阶**（M=128→160 跨界）：M=160/224 掉到 8.66/8.84（比 M=128/256 各低 ~10%）——**跨 wave 的形状（⌈M/128⌉ 变化但 tile 数不满整波）是最差形状**：多付一整波的启动成本却只多算很少的行。
2. M=96（9.15）< M=128（9.67）但同 tiles：M 增大 flop 增大而 tile 数不变 → 利用率单调升——**同 wave 内尽量取满 tile**。
3. tiles≥192（4 波）后稳定 9.8-10.0 TF：**波数≥4 时量化损失摊薄到 <5%**，与理论（最后不满波占比 ≤1/4）一致。
 4. **E1a（K=2048）与 E1b（K=4096）的重叠形状没有一致的 K 效应**：M=64 处 7.97 vs 7.96（持平，launch 主导区 K 不敏感）、M=256 处 9.45 vs 9.98（+5.6%）、但 M=512 处 10.07 vs 9.00（**反向**）。直觉上的「K 越大每 tile 摊薄装载、效率越高」在本数据对上**不成立**——重叠点的差异被会话噪声（±7% 带）与 cuBLAS 启发式（E1a 的 (1024,4096)=8.90 凹陷）淹没。结论：**跨实验的形状对比必须同会话同协议**，本 AR 只在实验内部比较（红线）。

## fig2 — skinny 边界（E2，N=K=4096）

**数据**：M=1..32 带宽平台 360-386 GB/s（80-86% 峰值）；M=64 过渡（269.6 GB/s，8.36 TF）；M≥128 算力平台 9.7-10.2 TF（87-91% 峰值），带宽跌至 168→28.5 GB/s。

**分析**：
1. **GEMV 区（M≤32）是纯带宽问题**：实测 360-386 GB/s ≈ 80-86% HBM 峰值。此时 TFLOPS 数字毫无意义（M=1 才 0.18 TF），**正确的指标是 GB/s**。decode 场景（M=batch=1..8）的算力利用率天花板就是 ~85% 带宽达成率。
2. **roofline 拐点实测吻合**：AI(M) = M·2048/(2M+4096) FLOP/B，AI=25 → M*≈51.2（图中绿线）；实测拐点恰在 M=32（仍带宽平台）与 M=64（269 GB/s，混合态）之间——**理论与实测在同一档采样内对上**。
 3. **cuBLAS 对 GEMV 没有摆烂**：M=1 时 359.7 GB/s 说明它选了带宽接近极限的 kernel（naive GEMV 理论上限就是流一遍 B：4096×4096×4B = 67.1MB，0.1866ms → 359.6 GB/s——实测 359.7 恰好贴住这条线，说明 A/C 的小流量被 L2/launch 重叠吸收，B 是唯一有效流量）。
4. **M=128 是本机 GEMM 的「满血起点」**：10.16 TF（91% 峰值）——比 E1a 的 128 方阵（2.32）高得多，因为 K=4096 摊薄了装载。**「多大算大」取决于 K**：AI 视角下 M·K 才是分子。

## fig3 — split-K：手工 vs 库启发式（E3 + E3seq，M=N=256，K=16384）

**数据**：s=1 单发 8.20 TF；s=2/4/8/16 手工 stream 并发 6.83/5.58/3.73/2.00 TF；**顺序执行对照（E3seq，默认流）7.57/6.68/5.30/3.56 TF**——手工 split 两种方式都单调变差、全败，且 **stream 版在每个 s 都比顺序版还慢**（-9.8%/-16.6%/-29.6%/-43.9%，随 s 放大）。

**分析**：
1. **本实验的最大收获是「反直觉基线」**：256×256 输出在 128×128 tile 模型下只有 4 个 tile → 4/48 SM → 饥饿上限 0.93 TF。但实测 s=1 = 8.20 TF（73% FP32 峰值）——**cuBLAS 内部已经自动 split-K**（等效 ~35 个并行 tile）。如果没识别这一点，会得出「split-K 没用」的错误结论；正确结论是「**你想要的 split-K，库已经替你做了**」。
2. 手工版为什么全败：(a) 每部分 GEMM（如 s=16 时 256×256×1024）本身又回到饥饿态，且 cuBLAS 对每个小调用**又**做了内部 split → 多层 split 互相打架；(b) **E3seq 对照实测**：多流不但没有带来并发，反而比纯顺序慢且随 s 单调放大——WDDM 上跨流提交/事件同步是净开销（此前「串行化」只是推测，现在有了顺序对照的定量支持）；(c) 归并（copy + 逐个 add_）在默认流串行执行，s=16 时 16 次小 kernel 的开销超过 GEMM 本体。顺序版同样全败说明**主因是 (a)+(c) 的「多层 split 打架 + 归并开销」，多流是额外的负贡献**。
3. **方法论红线**：手工优化的对照基线必须先证明「基线没有偷用你想优化的机制」；并发归因必须有**顺序对照实验**（E3seq），否则「WDDM 串行化」只是无法证伪的推测。CUTLASS 的 split-K 是模板参数 `split_k_slices`（08 示例里 =1），库启发式把它藏在了 runtime 层——**模板库 vs 运行时库的启发式透明度完全不同**（面试点）。

## fig4 — batch GEMM vs flat（E4）

**数据**：B=1/2 时持平（1.11 vs 1.08；2.63 vs 2.39）；B≥4 flat 一致胜出：4→5.21 vs 3.18（+64%），8→6.72 vs 6.00，16→6.95 vs 6.47，32→8.90 vs 8.47，64→9.75 vs 8.61（+13%）。

**分析**：
1. **flat 大 GEMM 几乎全面占优**：等价 flop 下，把 B 个小矩阵堆成 (B·256)×256 的「长条」让 cuBLAS 用普通 tile 调度，比 batched kernel 的按组调度更高效。256×256 每组只有 4 tile，batched kernel 的组间调度（index 计算 + 边界判断）是纯开销。
2. **B 越小差距越大**（B=4 时 +64%）：batched kernel 的固定开销被更少的组摊不平；B=64 时组数多到调度开销占比下降（+13%）。
3. **什么时候必须用 bmm**：权重各组不同且无法堆叠（每组独立 W）、或组数巨大且单组极小（strided batch 的显存/调度优势）、或必须避免 reshape 拷贝。**性能不是理由**（本机 FP32 256² 组合下）。
4. 注意 b=1/2 的「持平」是 launch 主导区（<0.05ms），无统计意义。

## fig5 — 数据类型断层（E5）

**数据（图 = JSON 当前值，即复跑第 2 次）**：FP32：5.38 / 9.53 / 10.46 / 9.69 TF（512→4096）；FP16 TC：7.01 / 44.29 / 67.43 / 60.67 TF。INT8 不可测（torch._int_mm 在 Windows torch 2.5.1 构建中未实现：`addmm_cuda not implemented for Int`，env.json 留档）→ 178.4 TOPS 只画理论线。

**多观测记录（同脚本两次完整 E5 + AR002）**：

| 配置 | 观测 1（首跑） | 观测 2（复跑，=图） | AR002 | 波动 |
|------|--------------|-------------------|-------|------|
| FP32@512 | 6.13 | 5.38 | — | ±12% |
| FP32@1024 | 9.65 | 9.53 | — | ±0.6% |
| FP32@2048 | 9.49 | 10.46 | 9.468 | **±10%（含跨会话）** |
| FP32@4096 | 9.64 | 9.69 | — | ±0.5% |
| FP16@512 | 9.79 | 7.01 | — | ±17% |
| FP16@1024 | 44.41 | 44.29 | — | ±0.3% |
| FP16@2048 | 65.46 | 67.43 | 54.87 | 跨会话 54.9~67.4 |
| FP16@4096 | 61.60 | 60.67 | 63.14 | ±2% |

**分析**：
1. **断层结构稳定**：FP32→FP16 同形状断层在两次观测中为 **6.9× / 6.4×**（@2048：9.49→65.46、10.46→67.43），接近硬件 8×（11.2/89.2）——tensor core 收益的方向与量级完全稳健，单点数字有带宽。
2. **大形状复现极好、小/中形状带宽大**：@1024/@4096 两次差 <1.5%（且与 AR002 衔接），@512/@2048 差 10-17%。机制：2048³ 单次 1.7ms，10 reps 循环仅 ~17ms——**测量窗口短于时钟爬坡时间**，测的是「当前时钟态」而非稳态；@4096 的 70ms 窗口足以稳住。这把 AR002 的「会话噪声带」结论推进了一步：**噪声带宽度是测量窗口长度的函数**（本 AR 的方法学新发现）。
3. **FP16 跨会话带（54.9~67.4，含 AR002 与轻烧机复测 58.4）**：烧机程度与时钟态主导；10s 空闲后直接掉到 3.4 TF（idle 降频）。FP32 大形状仅 ±1.5%（未推到功率墙）。**报 TC 数字必须带时钟态条件**。
 4. **FP16@4096 < @2048 稳定复现**（61.6/60.7 vs 65.5/67.4，两次分别 -5.9%/-10.0%）：大形状持续负载触发功率/热稳态回落——FP16 推到功率墙的证据（FP32 无此现象，两次观测方向一致：9.64/9.69 持平或微降）。
5. INT8 降级说明（诚实记录）：sm_75 硬件有 INT8 TC（08_turing 示例即 INT8），本机测不到是 **Windows torch 构建缺 cublasLt INT8 路径**，不是硬件缺失。CUTLASS 08 示例的 INT8 m8n8k16 路径源码可查（见 cutlass-turing-dissection.md）。
6. 与 AR002 口径衔接：FP32@2048 跨会话带 9.47~10.46（AR002 9.468 + 本 AR 两跑）；FP16@2048 跨会话带 54.9~67.4——两 AR 数字都真，**条件（时钟态/测量窗口）不同**。AR002 的「FP16@2048 ≈ 54.9」应加注「轻预热条件」。

## fig6 — L2 驻留效应（E6，per-iter event 协议）

**数据**：N=512（ws 3MB = 0.75×L2）：flush 3.81 TF vs no-flush 4.28 TF（**×1.12**）；N=1024（12MB=3×L2）：×1.02；N=2048（48MB）：×0.98；N=4096（192MB）：×0.99。

**分析**：
1. **只有工作集 < L2 时驻留才有可测收益，且只有 12%**：比直觉弱——因为 GEMM 的 K 循环**内部本来就有 L2 复用**（A tile 沿 M 复用、B tile 沿 N 复用，一个 128×128 tile 计算期间它的 A/B 列/行早被 L2 缓存），显式 flush 拿走的只是「迭代间」的残留复用，不是「迭代内」的。
2. **ws≥12MB 后 flush 与否无差**（×0.98-1.02，在 ±2% 协议噪声内方向不定——两组 3-pass 方向不完全一致，不下结论只报范围）：工作集远超 L2 时每次迭代天然自我驱逐。
3. **协议注意**：本实验用 per-iter event（每次迭代独立打点+同步）控制缓存态，绝对 TF 比 E5 的循环协议低 ~20%（N=512 no-flush: 4.27 vs E5 FP32@512 5.38；@512 本就是 ±12-17% 噪声格，差距量级而非精确值）——**同步开销在小 kernel 上不可忽略，两协议的数字不可混比**（红线）。
4. 实践含义：推理服务里「权重常驻、激活小」的场景，把热数据控制在 4MB 内有 ~10% 级收益；超出后不必为 L2 做额外设计。

## fig7 — operand layout（E7，2048³ FP32）

**数据**：colA_B 10.38 > AtB 10.31 > AtBt 10.28 > colA_colB 10.26 > AB 10.22 > ABt 9.95 > A_colB 9.88。极差 ×1.051（5.1%），无隐式拷贝（memory_allocated 断言通过）。

**分析**：
1. **「TN 最快」的祖传经验在本机/本代不成立**：七种组合（四种 op 组合 + 三种存储变体）全在 5% 内。sm_75 的 `ldmatrix` + swizzled shared 布局让 cuBLAS 对任意 layout 都能做无冲突装载，layout 不再是主要矛盾。
2. **唯一可辨的结构：B 侧转置微慢 ~3%**（ABt 9.95、A_colB 9.88 是仅有的两个 <10 的）：B 在 K×N 中沿 N 不连续（或等价地列主），shared 装载的 global→shared 路径少了点 coalescing 余量。A 侧转置无惩罚（AtB/colA_B 反而最高，噪声内）。
3. **图例映射（供笔记）**：torch row-major 世界里 `A.t()` 视图 → cuBLAS 收到「转置 op」，不拷贝（断言验证）；`colX` 变体是**同数学、不同存储**（预拷贝出列主 buffer 再取 .t() 视图），证明存储布局与视图 op 在 cuBLAS 内部殊途同归。
4. 实践含义：**为「布局对齐」做的 transpose/copy 几乎一定亏**（copy 本身的带宽和时间远超 3% 的核内差异）——除非下游多次复用。
